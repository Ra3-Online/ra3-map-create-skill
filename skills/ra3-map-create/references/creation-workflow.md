# 制图需求与分阶段流程

面向新建地图、整图改造和局部美化。先读用户已有对话，再读本页；只补充会影响结果的缺项。地图类型与尺寸未知时，不自动套用双人热带遭遇战。已知要求、用户修正和明确禁令优先于案例、脚本默认值与本页示例。

## 1. 把要求写成 brief

使用 [brief-schema.json](brief-schema.json) 的字段记录需求。`null` 表示尚未确定，不能当作“没有”或数字 `0`。`decisions` 标出用户要求、原图事实、参考证据或临时假设。机器结构用于防止遗漏；向用户只展示简短中文说明，不要求用户填写 JSON。收集阶段（`collecting`）可把 MOD 名称和改图来源记为 `null`，并登记待回答问题；进入规划或执行阶段后，已选择 MOD/改图的任务必须补齐对应名称/来源。

必须区分三件事：

- **玩法用途**：竞技、战役、娱乐、场景展示或其他。决定经济、出生点、任务和验收。
- **复现目标**：原创、参考现实、历史复刻、参考图片或已有地图。现实复刻仍可能是竞技或战役；不要把它当作与玩法互斥的唯一选项。
- **交付范围**：只有场景，还是可运行的遭遇战或带任务脚本的战役。漂亮场景不等于完整战役；脚本未做时明确写“场景版”。

旧图的模式、尺寸和资源通常可以读取。读取事实不能替用户决定要不要改变玩法。用户只要求一条街的美化时，不重问全图类型、尺寸，也不重建全图。

### 分阶段提问表

一次优先问当前阶段的 1–3 个关键问题；允许用户一次回答多项，后续跳过已回答内容。以下为提问内容，不是必须逐字发送的问卷。

| 顺序 | 需要确定什么 | 提问示例 | 哪些内容不能擅自补上 |
|---|---|---|---|
| A 用途 | 玩法、复现目标、交付范围 | “这张图主要用于竞技、战役、娱乐还是场景展示？若是复刻，请注明地点和时期；若是战役，需要任务脚本还是先做场景？” | 不因有城市就认定战役；不因用战役样例就复制任务基地 |
| B 基本信息 | 可玩宽高、原版/起义/MOD、新建或改图、目标文件 | “可玩区域多大？使用原版还是指定 MOD？是在原图上美化还是新建？” | 不自动用 320×320；不把含边框的数组尺寸当可玩尺寸；不覆盖同名旧图 |
| C 地域与季节 | 地点、季节、建筑语言、城市/乡村/港口等子场景 | “地点和季节是什么？主要做城区、乡村、自然地貌还是混合场景？” | 雪地不自动等于俄国；日式庭院与浮岛科技要塞不是同一套物件 |
| D 地形与水域 | 不规则起伏/规则台地/平地、层级、斜坡、湖河海范围、桥梁 | “地形希望自然起伏还是清楚的高地低地？是否有河湖或临海，约占多大范围？需要哪种桥梁？” | 不自动加湖或桥；道路穿过水面不等于可通行桥；水位不能只按第一片水域推断 |
| E 建筑与绿化 | 建筑密度、建筑/装饰分别是否可缩放与重叠、绿地范围、树种丰富度 | “建筑希望疏、中还是密？民房与装饰是否分别允许缩放、重叠？绿化希望集中公园还是分布在街角与院内，树种偏统一还是丰富？” | 民房许可不能推广到装饰，反之亦然；“密集”不表示可互相穿模；丰富不表示混入异地植物 |
| F 渲染气氛 | 时段、雨雪、雾、色调、云影、泛光和场景特效 | “希望白天、黄昏还是夜间？是否需要雨雪、薄雾、云影或特定色调？” | 不把灰白滤镜当冬季材质；不虚构天气枚举、体积云、火车运行或自动道口效果 |

若用户明确说“你自行决定”“按样例来，先做草稿”，可以补出非指定选项，并在 `decisions` 写清假设和依据；仍需遵守其所有限制。不要在每个可撤销编辑前要求审批。涉及新图用途、可玩尺寸、指定 MOD 未挂载或互相矛盾的硬性要求时，先解决依赖，再执行依赖它的批量编辑。

### 提问不是停工

等待关键答案时可以检索当前资源、只读分析可用样例、查看真实模型和材质、准备有标注的布局备选。不要提前写入目标地图，再拿既成草稿迫使用户接受一个默认玩法。简单偏好未回答时，说明假设并继续有依据的部分；不能把等待超时当成用户同意。

## 2. 从 brief 转成可画的布局

把每个主要区域写成一行：**用途 → 所在高程 → 建筑/地表 → 出入口 → 相邻关系 → 要检查的画面**。坐标与尺寸在真正放置前由当前地图和实际模型确定；图片中的像素不是世界坐标。

例：医院街区 → 中层台地 → 医院、前庭铺装、围墙与绿化 → 面向支路的入口 → 邻近住宅但留救护车/行人通路 → 门前、围墙门口与街道近景。

先确定三种关系：

1. **全图结构**：区域与水域的位置、地标、主要路线、可通行高差。竞技另定出生与经济；战役另定任务动线。
2. **街区或自然分区**：道路等级、建筑退距、院界、公园、林缘、岸线、功能地表。
3. **局部关系**：入口接路、灯照向路面、座椅面向步行空间、垃圾桶靠服务点、围墙不封门、船接近合理码头。

“填满空地”不是完成标准。每一片空地先说明用途：公园、广场、雪地后院、空置工地、堆场、坡地或任务留白；再补符合用途的贴图和小物。若用户要求全市区，避免用大片未说明的空地代替街区，也不再自动安排郊区。

### 类型决定分支

| 用途 | 必须保留或确定 | 不自动加入 | 主要验收 |
|---|---|---|---|
| 竞技/遭遇战 | 人数、出生点、玩家、资源、基地展开、陆海路线与多人元数据 | 样例战役的驻军、任务触发和初始基地 | 经济/通路数据、实际开局、采矿与单位通行；平衡仍需对局 |
| 战役 | 任务方与目标；若只做场景则记录尚无任务脚本 | 矿脉、对称经济、两方基地与连续 Player_1..N 的遭遇战约束 | 场景结构、任务动线；有脚本才检查胜负与触发流程 |
| 娱乐 | 人数、规则、特殊目标、哪些资源可用、是否依赖 MOD | 未确认的常规经济或胜利规则 | 特殊规则能否运行、可达性与视觉可读性 |
| 现实/历史复刻 | 具体地点、时期、参考来源、精确到什么程度、哪些替代允许 | 与时期明显冲突的标志性资产；强制对称 | 城市结构和地标关系、比例/朝向、替代资产说明；玩法另按其用途验收 |
| 局部美化 | 原图范围、保留项、目标风格、输出副本 | 玩家、资源、任务、尺寸和玩法重排 | 源文件保持、指定区域画面、原有功能没有被装饰阻挡 |

## 3. 按区域选资源，先验证小样

读取“地域＋季节”参考后，再读取所需子场景，不把所有候选混进一张图。资源表应区分：样例出现过、当前目录存在、模型实际显示、放置关系实际验证。四者不可互相替代。

- 建筑：看原生尺寸、入口/正面、本地轴向与地面接触。不是每个模型都沿本地 X，也不是模型包围盒中心就是放置原点。
- 围墙、悬崖、海墙与铁路：做含直段、接头/转角和开口的小样，核对端面对接、基础高度、出入口与通行。
- 道路：先验证直段、拐角、T 字口和坡道接头。道路、边饰、标线、地表铺装分别记录。
- 地表：先验证底纹、辅纹、两材质交界和三材质交点。画面仍有三角齿时不能以混合命令成功当作解决。
- 设施：选医院、车库、港口、车站、公园等功能样板，入口连到路，再补家具与车辆。

小样可在新的草稿副本或目标图的计划区域制作。少量放置和看图通过后再扩展；不要一次批量铺满全图，最后才发现围墙原点或灯的朝向错了。

## 4. 制作阶段与进入下一阶段的条件

顺序是为了避免把未验证缺陷复制到全图；用户只要求局部编辑时跳到对应阶段，不强制重做前面已经合格的工作。

| 阶段 | 实际动作 | 可以继续的证据 | 暂停依赖它的操作 |
|---|---|---|---|
| 需求 | 填 brief；标记未知与已授权假设 | 用途、可玩尺寸、目标版本和编辑范围明确 | 用途/尺寸未知、硬性要求互相矛盾、目标 MOD 未挂载 |
| 地形/水域 | 建层级、坡道、岸线和任务/玩法路线 | 逐格高程与通行标志；总览、剖面或 3D 说明层级与连接实际存在 | 关键区域无连接、桥仅外观跨水、目标台地不能容纳用途 |
| 道路/地标 | 主路、铁路、桥和主要功能建筑 | 原生尺寸与端点正确；道路接头、门前和高差连接近景可用 | 接头断裂/尖刺、建筑压路、悬浮/埋地、关键桥未验证 |
| 地表 | 有用途的连续主面/辅面与局部边缘处理 | 同机位查看清晰硬边和自然软边；刷过的材质未异常丢失 | 接缝有重复锯齿、旧纹理被覆盖、三材质交点错乱 |
| 装饰/绿化 | 各子场景按功能补家具、院墙、植被、车辆和磨损 | 行人/车辆入口不堵；朝向、原生比例、季节和区域用途相符 | 穿模、灯照向房后、围墙堵门、资产堆积掩盖错误 |
| 环境 | 使用实际支持的光照、雾、云影、后期与天气 | 参数可读回；资源存在；与原始色调同机位对照，不靠特效遮缺陷 | 效果名/类型/资源未知；只有编辑器预览，未有游戏证据却声称游戏一致 |
| 交付 | 保存、关闭重开、支援文件、截图与报告；按 game-compatibility 查目标 WB 与游戏 | Core、WB 稳定加载、游戏启动及单项玩法分别有证据或标记未检查；文件实际存在 | 保存失败、支援文件错误、已知运行失败未记录、明显视觉缺陷未记录、把场景版称完整战役 |

某区域遇到工具/渲染缺陷时，可继续不依赖该缺陷的区域。记录位置、现象、最小复现和未通过项。进行有新依据的局部修正并重拍；相同参数的重复命令不能算新的尝试。两次同方法没有可见改善时，停止扩大该方法，保留可查看版本，改用新的证据或报告限制。没有完成的阶段不标记通过，也不把“保存成功”升格为“画面合格”。

格式或道路小样出现目标 WB 退出时，按 [游戏兼容验收](game-compatibility.md) 保留版本并做获准副本的增量隔离；不要继续批量复制该组合，也不靠另一遍 Core 保存关闭问题。单人任务的一处出生点按任务需求保留；需要遭遇战验证时另建明确标记的双位测试副本，不把测试副本替换原单人作品。

## 5. 天气、滤镜、云与特效的真实能力

工具名和参数以连接后列出的 schema 为准。下表表示当前接口能力，不保证未来版本、所有资源或游戏内效果相同。

| 请求 | 实际读取/编辑入口 | 可作出的承诺与需要检查的内容 |
|---|---|---|
| 清晨/白天/黄昏/夜晚，太阳方向与色调 | `ra3map_get_lighting` / `ra3map_set_lighting` | 当前时段 `time` 是 1–4，`configIndex` 是 0–3；用当前 schema，不混用下标；保存重开及阴影近景检查 |
| 距离雾 | `ra3map_get_fog` / `ra3map_set_fog` | RGB 为 0–1、start≤end；雾不能用来遮住空地、接缝或缺模型 |
| 云影、宏观纹理 | `ra3map_get_env_data` / `ra3map_set_env_data`；目录资源查询 | 云贴图是地表云影/环境设置，不能因此承诺可见体积云、任意云速；两个未知数值保持原值 |
| 泛光、查色滤镜、失真 | `ra3map_get_post_effects` / `ra3map_add_post_effect` / `ra3map_set_post_effect` | 已有模板是 Bloom、LookupTable、Distortion；LookupTexture 必须查目录。参数写回通过仍要看图/游戏；不自造效果名称 |
| 雨、雪等天气 | `ra3map_world_info` / `ra3map_set_world_info_prop` 的 `weather` 属性 | 天气为整数记录，不凭名称猜枚举。先取得该版本菜单或已验证样例中的值并验证；未验证时只登记请求，不能称雨雪已实现 |
| 烟、火、灯光、动画装饰 | 当前对象目录、模型预览与放置工具；有脚本需要时读脚本接口 | 目录里存在对象不证明效果/动画能播放。查真实候选并试放；自动道口、火车运行等还需脚本/游戏测试 |
| 水色、反射与流动 | `ra3map_get_water`、`ra3map_get_global_water_settings` 及对应编辑工具 | 先保留并读取合法样例参数，修改已明确字段；编辑器水面是近似，不能承诺等于游戏倒影 |

### 其他真实提示的处理示例

- **“做张漂亮地图。”** 先问用途/交付范围，再问尺寸和游戏版本，再补地域季节；可只读查看资源，不先创建默认双人图。用户把设计交给 AI 时写出选择依据。
- **“原版 1v1，400×400，尤卡坦夏季，十个矿，岛屿地形，别太平。”** 不再问类型/尺寸/版本/地点/季节。确认是岛屿陆战还是分岛海战及需要的连接；设计有用途的台地、坡道和海湾。十矿是本图要求，不能改成脚本默认六矿。
- **“把这张日本浮岛图变成三层海上钢铁要塞。”** 读取旧图可玩范围与现有功能；先确认保留的任务/玩法和平台连接，再用浮岛科技风格资产做一段平台—悬崖饰面—边缘栏杆小样。不要套传统日式民房/庭园，不在海面刷钢铁纹理就称平台可通行。
- **“只把医院周围美化，原图和任务别动。”** 只核对医院和需要改的范围，另存副本。入口/通路/候车停车空间/围墙开口先于垃圾桶和花坛，不提整图经济问卷。
- **“夜间俄国冬季城镇，想有飘雪和火车经过。”** 先补用途、尺寸等关键缺项。把“飘雪”和“火车运行”记为待验证能力；夜间光照可用实际接口调整。不能用静态火车摆放冒充经过动画。

## 7. 面向较弱模型的执行自检

执行下一批编辑前，回答以下五项。任何一项不能回答，先查工具/看图/补需求，不凭常识补资源名称。

1. 我正在做哪种用途、哪一阶段、哪一个区域？
2. 本批是否改变了用户禁止改变的民房尺寸、旧图玩法、经济或文件？
3. 资源是否属于当前版本，实际模型是否可见，朝向/接地是否验证？
4. 本批与道路、入口、高差、水位和邻接物件是什么关系？
5. 什么实际画面或数据能判断成功？失败后能否局部退回，不牵连全图？

验收记录只用：**通过 / 未通过 / 未检查 / 不适用**。不给未知效果、未看近景或未运行游戏的项目打“通过”。最终说明包含实际文件、已完成范围、未通过项和游戏内测试状态；无需读者翻历史消息才能理解地图的状态。
